# ADR 架构决策记录规范

先查目标仓库的 `AGENTS.md` 与已有 `docs/adr/`，沿用项目现有的目录、编号宽度、状态词和语言习惯；没有既有约定时按本规范执行。

## 先判断要不要写

| 该写 ADR | 不写 ADR |
| --- | --- |
| 改变架构、服务边界、数据模型或外部协议通道 | 普通修 Bug、单点功能迭代 |
| 推翻、收缩或部分废止既有设计决定 | 常规样式、文案或参数微调 |
| 有明显方案取舍，未来容易被质疑「为什么不那样做」 | 一次性排查笔记、个人待办、过程流水账 |
| 多步骤大重构需要定清拆块顺序、验收门槛与收尾判据 | 纯依赖升级或常规重构（未改变边界） |

不够格就不写：临时进度留在会话、Issue 或仓库外，不向仓库堆带日期的过程文档。

## 文件与头部

默认路径：`docs/adr/NNNN-<english-slug>.md`（4 位零填充递增，取当前最大编号 `+1`；空目录从 `0001` 起）。

```markdown
# ADR-NNNN：结论式中文标题

- 状态：Accepted
- 日期：YYYY-MM-DD
- 关系：[ADR-XXXX](XXXX-slug.md)（可选；修订旧决定时改用「修订：」）
```

- 标题写**决定了什么**，不写「关于 X 的讨论」或「X 方案调研」。
- 状态按需取 `Proposed`、`Accepted`、`Deprecated`、`Superseded by ADR-XXXX`；待分步开工可注 `Accepted（待开工）`。

## 正文结构

单篇控制在 2–6 KB，只写结论、事实依据与取舍，不贴长段代码或原始日志。

1. **背景**：问题、约束与实测数据；有数字或规模统计时标注测量日期。
2. **决定**：编号列出具体边界、归属与执行规则。
3. **放弃方案 / 不做什么**：写清否决了什么及原因，防止未来重复踩坑。
4. **后果 / 影响**：联动变更的文档、模块与调用方重写成本；有真机或线上实测结果时补 **验收** 一节。

**大重构拆步型**（替代长任务进度文档）：在「决定」里额外写明 **拆块顺序（零行为变化优先）**、**每块验收命令** 和 **明确收尾判据**（如旧目录消失或指标归零），推进进度由原子提交与代码状态体现，不在 ADR 里逐日写日记。

## 演进与文档边界

- **只追加，不重写历史**：推翻或修改旧决定时新建一篇 ADR 写明哪些条款作废，并在旧 ADR 头部回指新编号。
- **常态文档只写最终态**：`README`、`docs/`、契约文档和代码注释只描述当前成立的事实；「为什么从 A 改成 B」收敛在 ADR 中。
- **同步联动**：若决定改变了契约、运维或复用清单，在同一改动中更新对应文档，并在 ADR 的「影响」里指明。

## 自查

```sh
scripts/check-adr                  # 体检当前仓库 docs/adr（只报不改）
scripts/check-adr path/to/adr      # 指定 ADR 目录或批量扫描多仓库
scripts/check-adr --next           # 输出下一个可用 4 位编号
```

细则全文见 `references/rules.md`，脱敏 bad→good 对照见 `references/examples.md`。
