# ADR 真实场景对照（脱敏示例）

以下示例提炼自真实工程实践，项目与业务名已泛化处理，重点展示「怎么定边界、怎么修订旧 ADR、怎么用 ADR 替代过程流水账、以及什么不该写 ADR」。

---

## 1. 标题空泛、缺少放弃方案 → 改为结论式标题 + 明确反例

### 坏例

```markdown
# ADR-0001：后端架构重构方案

## 说明
我们决定把老的 HTTP 服务迁移到新的 Web 框架，这样代码更清晰，以后也更好维护。
前端也先不动，等后面再说。
```

问题：缺少状态与日期；标题没说清决定了什么；只写「更清晰、更好维护」这类空话；没写否决了哪些诱人但危险的方案（例如一次性重写或拆微服务），三个月后很容易被人重新推翻。

### 好例

```markdown
# ADR-0001：后端渐进迁至模块化单体框架，保持单进程部署

- 状态：Accepted
- 日期：2026-08-14

## 背景

旧版 HTTP 服务将业务逻辑、流媒体 Range 与错误响应耦合在底层请求处理器中，直接整站重写会使现有核心播放路径失去回退手段。

## 决定

- 后端按模块渐进迁移至新框架，代码按职责分层，运行态保持单进程、单体部署。
- 第一阶段仅迁移健康检查与 JSON API，流媒体与页面路由在切换验证通过后移除旧实现。
- 在进程内缓存与写锁迁出全局变量之前，仅允许单 worker 运行。

## 放弃方案

- **一次性全量重写**：回退成本过高，核心链路不可中断。
- **按前后端拆为独立微服务部署**：单机自托管场景下额外增加跨进程鉴权与运维复杂度，无对应收益。

## 后果

获得统一路由与契约层；单 worker 限制继续保留，后续可通过独立 ADR 推进状态外置。
```

## 2. 推翻旧决定时直接覆盖原文 → 改为新建 ADR 并双向互链

### 坏例

直接打开旧的 `0018-anonymous-api-with-cookie-fallback.md`，把整篇正文删掉重写成「现在改走账号登录 JWT 接口」。

问题：Git 历史里虽然能翻，但读文档的人完全看不出为什么旧方案失效，也容易在代码里漏删旧方案残留的 Cookie 配置。

### 好例

新建 `0025-switch-to-authenticated-api.md`：

```markdown
# ADR-0025：上游数据读取从网页与 Cookie 改走登录接口

- 状态：Accepted
- 日期：2026-11-11
- 修订：[ADR-0018](0018-anonymous-api-with-cookie-fallback.md) 第二条、第四条

## 背景

2026-11 上游将列表筛选与排序能力迁至登录后接口，匿名签名接口不再响应筛选参数；原有网页通道依赖人工定期粘贴 Cookie，成为整条链路唯一无法自愈的凭据。

## 决定

- **一、登录接口成为唯一读取通道**：凭据收敛为账号密码换取短期令牌，失效自动重登，移除配置页中的 Cookie 输入项。
- **二、下线网页 HTML 解析**：列表、详情与搜索适配器统一走 JSON 接口，删除旧正则解析代码。

## 放弃方案

- **继续保留匿名接口 + 网页 Cookie 双通道**：维护两套解析逻辑且人工 Cookie 仍会周期性失效。

## 影响

- [ADR-0018](0018-anonymous-api-with-cookie-fallback.md) 的「二、保留网页 Cookie 备用」「四、不引入账号」作废，其余条款继续生效；
- 同步更新采集文档，移除旧限制说明与 Cookie 配置入口。
```

同时在旧 `0018-anonymous-api-with-cookie-fallback.md` 头部补充一行指针：
`- 状态：Accepted（第二、四条由 [ADR-0025](0025-switch-to-authenticated-api.md) 修订）`。

## 3. 写 120 KB 过程流水账 → 改为 5 KB 重构拆步型 ADR

### 坏例

新建 `work/11-18-ui-kit-refactor-progress.md`，每做一步都追加「第 1 轮调研日志」「第 2 轮改完失败的报错栈」「第 3 轮修改后的文件列表」「待办 42 项」，最终膨胀到 130 KB，任务结束后还要手动搬进 `work/archive/`。

### 好例

写一篇简洁的重构拆步型 `docs/adr/0030-shared-controls-to-components.md`：

```markdown
# ADR-0030：共享控件按状态边界拆为纯函数、Hook 与组件

- 状态：Accepted（待开工；逐块交付，每块一个可回滚提交）
- 日期：2026-11-21
- 关系：[ADR-0010](0010-frontend-framework-migration.md)

## 背景

遗留目录 `src/ui-kit/` 包含 9 个模块、共 1729 行命令式 DOM 工具，虽然已搬进新前端目录，但组件仍需在副作用里手工接线。

## 决定

### 1. 按状态归属分三类

| 类型 | 判据 | 目标位置 |
| --- | --- | --- |
| 纯模板工具 | 输入数据返回字符串，不碰 DOM | `core/` |
| DOM 增强 | 给既有元素挂行为，不拥有节点生命周期 | `components/use-*.ts` |
| 有状态浮层 | 自行管理开合、焦点与确认结果 | `components/*.tsx` |

### 2. 拆块顺序（零行为变化优先）

1. 纯模板工具迁入 `core/`（仅改 import）
2. 滚动与快捷键等 DOM 增强改写为 Hook
3. 下拉菜单改为现成无障碍菜单组件
4. 弹窗类最后改写为声明式确认状态，同步更新调用点

### 3. 每块验收门槛

每块交付需通过类型检查、单测、生产构建，并在本地浏览器核对受影响页面无控制台错误。

### 4. 收尾判据

`src/ui-kit/` 目录彻底移除，全部 59 个导出归入上述三类之一。

## 不做什么

- 不把纯字符串辅助函数强行改写为组件；
- 不为单个浮层引入新的第三方 UI 库。
```

之后每一块只做干净的原子提交，看 `git log` 和 `src/ui-kit/` 还剩几个文件即可确认进度，零流水账负担。

## 4. 不该写 ADR 的反例

以下场景直接走代码提交与测试，**不要建 ADR**：

- 「修复导出按钮在空列表时返回 500」→ 属于缺陷修复，进 `fix(export): ...` 提交与单测。
- 「把列表分页默认值从 20 改成 50」→ 未改变架构边界，直接改配置与常规文档。
- 「今天在测试环境抓包排查超时问题的 5 次尝试记录」→ 属于一次性排障材料，放会话或仓库外目录，结论若导致协议/重试策略变化，再把最终决策浓缩进 ADR。

## 常见症状对照表

| 症状 | 对应规则 |
| --- | --- |
| 标题写「关于 X 的方案讨论」 | 改为结论式标题，写清拍板了什么 |
| 只有「背景 + 方案」，没写否决项 | 补「放弃方案 / 不做什么」，挡住未来走回头路 |
| 改旧设计时直接覆盖旧 ADR 正文 | 改为新建 ADR 并在新旧两处双向互链 |
| 单篇超过 15 KB，塞满每日进度与日志 | 剥离过程态，改用拆块顺序 + 收尾判据 |
| 修个小 Bug 也建 `ADR-0048` | 先过准入表：不涉及边界、取舍或长期约束就不写 |
